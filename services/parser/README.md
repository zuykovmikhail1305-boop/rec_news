# Сервис сбора публикаций — первый этап

Общий конвейер: URL → адаптер источника → загрузка HTML → извлечение текста.
ML/LLM не используется. Адаптеры: Банк России, ТАСС, Интерфакс, Ведомости, Коммерсантъ.

- ЦБ: `https://www.cbr.ru/press/event/?id=...` и `/press/pr/?id=...`.
- ТАСС: `https://tass.ru/раздел/числовой-id`.
- Ведомости: `https://www.vedomosti.ru/раздел/news/YYYY/MM/DD/id-slug`
  и аналогичные `/articles/` (только открытые публикации).
- Интерфакс: `https://www.interfax.ru/раздел/числовой-id`.

Принимаются отдельные публикации, главные страницы и списки возвращают 422.
На реальной странице проверен ЦБ `/press/event/?id=32923`. Для Интерфакса
23 октября 2026 проверены через /parse публикации `/business/1124550`,
`/business/1124541`, `/business/1124538`: заголовки, даты и все абзацы текста
сверены с HTML. Канонический хост Интерфакса — `www.interfax.ru`.
ТАСС пока проверен на синтетическом HTML; актуальные реальные страницы
ещё требуют проверки. Отказы источника возвращаются как ошибки, без обхода защиты.

## Эндпоинты

`POST /parse` — загрузить публикацию и вернуть заголовок, **текст**, источник,
канонический URL, дату/время (если они указаны в HTML) и версию парсера.
Этот обработчик не обращается к БД и не сохраняет публикацию. Повторный запрос
заново загружает страницу. Отсутствующее время не выдумывается.

```json
{"url": "https://www.cbr.ru/press/event/?id=32923"}
```

`POST /collect` — тот же разбор плюс сохранение HTML и данных в БД, с пропуском
повторных публикаций. Формат входа тот же.

`parser_app/publications.py` содержит общий конвейер; `adapters.py` — правила URL
и особенности источников. Экстрактор на Trafilatura из прежнего TASS-сборщика
перенесён без изменения алгоритма в `parser_app/extraction.py`. Его теперь используют
как старый `app/tass_parser.py`, так и новые адаптеры ТАСС/Интерфакса.

## Запуск из корня репозитория (PowerShell, Python 3.11+)

```powershell
cd services/parser
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m uvicorn parser_app.main:app --host 127.0.0.1 --port 8001 --workers 1
```

Swagger: http://127.0.0.1:8001/docs. На Linux используйте `.venv/bin/python`.

```powershell
$body = @{url='https://www.cbr.ru/press/event/?id=32923'} | ConvertTo-Json
Invoke-RestMethod http://127.0.0.1:8001/parse -Method Post -ContentType 'application/json' -Body $body
```

Можно выполнить тот же сбор через CLI:

```powershell
.venv/Scripts/python -m parser_app 'https://www.cbr.ru/press/event/?id=32923'
```

## Результат и хранение

`POST /collect` принимает `{"url":"..."}` и возвращает `status`, `id`, `source`,
`url`, `title`, `text`, `published_date`, `fetched_at`, `content_hash`, `parser_version`.
Первый вызов — `ready`, повторный — `skipped` без повторной загрузки статьи.
Сохраняется HTML и его извлечённый текст. Уникальность контролируется по источнику
и каноническому URL. Совпадение текста разных публикаций не удаляет материалы.
Дата без времени хранится в `published_date`; `published_at` остаётся NULL.

`PARSER_DATABASE_URL` задаёт БД; по умолчанию `parser_app/parser.db`.
Таблицы `news_sources`, `news_raw`, `news_quotes` повторяют существующий контракт
парсера в `app/`, с дополнительной колонкой `news_raw.published_date`.
Используйте новую БД: автоматической миграции старой схемы нет.
Старый TASS-сборщик списков остаётся в `app/tass_parser.py`; извлечение отдельной
статьи делегировано общему модулю. Планировщик и обход списков в новом API отсутствуют. Таблица цитат создаётся для совместимости, но не заполняется.

Сетевые ошибки/HTTP-отказы/неподходящий HTML возвращают 502 и не создают готовую
публикацию. Некорректный или неподдерживаемый URL — 422. Пересекающиеся запросы —
409. Между вызовами обоих эндпоинтов API выдерживается общая пауза 5 секунд. Разрешены
только HTTPS и редиректы на публикации того же источника; защита сайтов не обходится.

Для синхронных `/parse` и `/collect` запускайте один API worker. Их локальный
rate limit не объединён с очередью; при регулярном сборе используйте `/queue`
и отдельный воркер вместо параллельного запуска синхронного CLI/API-сбора.
Очередь и автоматические повторы описаны ниже. Обход списков и RSS пока не реализован. API предназначен для локального запуска.

## Очередь обработки

Очередь хранится в `news_raw` той же БД `PARSER_DATABASE_URL`, что использует API.
Задачи сохраняются после перезапуска. Добавлена таблица `queue_source_state`
для общего ограничения частоты воркеров; она создаётся при запуске без изменения
существующих колонок и данных.

### Поставить URL

`POST /queue` возвращает HTTP 202 и текущие задачи; сам запрос ничего не загружает.
До 100 URL за запрос, весь пакет валидируется и сохраняется одной транзакцией.
Повторная постановка того же нормализованного URL возвращает прежнюю задачу,
сохраняет её статус и не обнуляет попытки (включая `failed`).

```json
{"urls":["https://www.interfax.ru/business/1124538"]}
```

`GET /queue` — список (параметры `status`, `limit`, `offset`).
`GET /queue/{id}` — статус, число попыток, ошибка, время повтора и готовый текст.

### Запустить воркер

Во втором терминале из `services/parser`, с той же настройкой БД, что у API:

```powershell
.venv/Scripts/python -m parser_app.worker
```

Воркер опрашивает БД раз в 2 секунды. Для одного прохода по доступным задачам:

```powershell
.venv/Scripts/python -m parser_app.worker --once --limit 20
```

`--once` не ждёт будущих повторов или освобождения лимита источника. Если задача
пока недоступна, она останется в БД для следующего запуска.

### Состояния и повторные попытки

- `pending` — ожидает обработки.
- `processing` — захвачена воркером, попытка началась.
- `ready` — HTML, текст и метаданные сохранены.
- `retry` — временная ошибка, ожидает следующей попытки.
- `failed` — постоянная ошибка или лимит попыток исчерпан.

Сетевые ошибки, 429 и 5xx: максимум 3 попытки, паузы 60 и 120 секунд;
`Retry-After` учитывается, если требует более долгого ожидания.
403, прочие постоянные HTTP-ошибки и ошибки извлечения автоматически не повторяются.
При 403/429 источник приостанавливается минимум на 15 минут; другие источники
продолжают обрабатываться. Ошибка сохраняется в `last_error` и видна в API.

Захват атомарный: одна задача не выдаётся одновременно двум воркерам. После
15 минут без завершения задача может быть захвачена снова; запоздалое завершение
старого воркера не перезаписывает новый результат. Если последняя попытка тоже
зависла, задача после истечения этого срока переводится в `failed`.
Между стартами задач одного источника — не менее 5 секунд, общее состояние в БД
для всех воркеров. Сетевой запрос выполняется вне транзакции захвата.

Параллельный захват проверен на файловой SQLite. При сбое между загрузкой и
сохранением повторный сетевой запрос возможен; новая строка публикации не создаётся.
Неожиданные внутренние ошибки пишутся в лог воркера, задача восстанавливается
после истечения срока захвата. Ручной перезапуск `failed` через API пока не добавлен.
