# Сервис сбора публикаций — первый этап

Общий конвейер: URL → адаптер источника → загрузка HTML → извлечение текста.
ML/LLM не используется. Адаптеры: Банк России, ТАСС, Интерфакс, Ведомости, Коммерсантъ.

- ЦБ: `https://www.cbr.ru/press/event/?id=...` и `/press/pr/?id=...`.
- ТАСС: `https://tass.ru/раздел/числовой-id`.
- Ведомости: `https://www.vedomosti.ru/раздел/news/YYYY/MM/DD/id-slug`
  и аналогичные `/articles/` (только открытые публикации).
- Интерфакс: `https://www.interfax.ru/раздел/числовой-id`.

Принимаются отдельные публикации, главные страницы и списки возвращают 422.
На реальной странице проверен ЦБ `/press/event/?id=32923`. Для Интерфакса
23 октября 2026 проверены через /parse публикации `/business/1124550`,
`/business/1124541`, `/business/1124538`: заголовки, даты и все абзацы текста
сверены с HTML. Канонический хост Интерфакса — `www.interfax.ru`.
ТАСС пока проверен на синтетическом HTML; актуальные реальные страницы
ещё требуют проверки. Отказы источника возвращаются как ошибки, без обхода защиты.

## Эндпоинты

`POST /parse` — загрузить публикацию и вернуть заголовок, **текст**, источник,
канонический URL, дату/время (если они указаны в HTML) и версию парсера.
Этот обработчик не обращается к БД и не сохраняет публикацию. Повторный запрос
заново загружает страницу. Отсутствующее время не выдумывается.

```json
{"url": "https://www.cbr.ru/press/event/?id=32923"}
```

`POST /collect` — тот же разбор плюс сохранение HTML и данных в БД, с пропуском
повторных публикаций. Формат входа тот же.

`parser_app/publications.py` содержит общий конвейер; `adapters.py` — правила URL
и особенности источников. Экстрактор на Trafilatura из прежнего TASS-сборщика
перенесён без изменения алгоритма в `parser_app/extraction.py`. Его теперь используют
как старый `app/tass_parser.py`, так и новые адаптеры ТАСС/Интерфакса.

## Запуск через uv (рекомендуется, PowerShell)

Корень проекта uv — `services/parser`, пакет с кодом — `parser_app`.
Выполняйте команды из корня сервиса:

```powershell
cd D:/repos/rec_news/services/parser
uv sync --locked
uv run scripts/init_db.py
uv run scripts/run_api.py
```

Во втором терминале из `services/parser`:

```powershell
uv run scripts/run_worker.py
```

Проверки:

```powershell
uv run scripts/init_db.py --check
uv run python -m unittest discover -s tests -v
```

`pyproject.toml` описывает зависимости, `uv.lock` фиксирует их версии,
`.python-version` выбирает Python 3.12. `uv sync` создаёт окружение автоматически.
Вложенное окружение `parser_app/.venv`, если оно осталось после прежних попыток,
при таком запуске не используется. Модули пакета отдельно как файлы не запускайте.

## Запуск через venv и pip (PowerShell, Python 3.11+)

```powershell
cd services/parser
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python scripts/init_db.py
.venv/Scripts/python scripts/run_api.py
```

Swagger: http://127.0.0.1:8001/docs. На Linux используйте `.venv/bin/python`.

Скрипты можно вызывать из любого рабочего каталога, указав путь к скрипту.
Окружение и зависимости устанавливаются один раз; при следующих запусках
достаточно `scripts/run_api.py` и, для очереди, `scripts/run_worker.py` во втором терминале.
На SQLite API и воркер по умолчанию создают отсутствующие таблицы. На PostgreSQL сначала выполните `scripts/init_db.py`.

`scripts/init_db.py` создаёт недостающие таблицы и проверяет наличие колонок;
повторный запуск сохраняет существующие записи. Он не загружает тестовые новости,
не скачивает модели; из старой схемы автоматически добавляется только nullable `news_raw.published_date`. Проверка без записи:

```powershell
.venv/Scripts/python scripts/init_db.py --check
```

Настройки передаются через переменные окружения (файл `.env` автоматически не читается):

- `PARSER_API_HOST` — адрес API, по умолчанию `127.0.0.1`.
- `PARSER_API_PORT` — порт API, по умолчанию `8001`.
- `PARSER_DATABASE_URL` — URL БД, один и тот же для API, инициализации и воркера;
  по умолчанию SQLite `parser_app/parser.db`, независимо от рабочего каталога.
  Для другой SQLite-базы используйте абсолютный путь и заранее создайте родительский каталог.

Аргументы `--host` и `--port` имеют приоритет над переменными окружения:

```powershell
.venv/Scripts/python scripts/run_api.py --port 8001
```


```powershell

Invoke-RestMethod http://127.0.0.1:8001/parse -Method Post -ContentType 'application/json' -Body $body
```

## Результат и хранение

`POST /collect` принимает `{"url":"..."}` и возвращает `status`, `id`, `source`,
`url`, `title`, `text`, `published_date`, `fetched_at`, `content_hash`, `parser_version`.
Первый вызов — `ready`, повторный — `skipped` без повторной загрузки статьи.
Сохраняется HTML и его извлечённый текст. Уникальность контролируется по источнику
и каноническому URL. Совпадение текста разных публикаций не удаляет материалы.
Дата без времени хранится в `published_date`; `published_at` остаётся NULL.

`PARSER_DATABASE_URL` задаёт БД; по умолчанию `parser_app/parser.db`.
Таблицы `news_sources`, `news_raw`, `news_quotes` повторяют существующий контракт
парсера в `app/`, с дополнительной колонкой `news_raw.published_date`.
Используйте новую БД: автоматической миграции старой схемы нет.
Старый TASS-сборщик списков остаётся в `app/tass_parser.py`; извлечение отдельной
статьи делегировано общему модулю. Планировщик и обход списков в новом API отсутствуют. Таблица цитат создаётся для совместимости, но не заполняется.

Сетевые ошибки/HTTP-отказы/неподходящий HTML возвращают 502 и не создают готовую
публикацию. Некорректный или неподдерживаемый URL — 422. Пересекающиеся запросы —
409. Между вызовами обоих эндпоинтов API выдерживается общая пауза 5 секунд. Разрешены
только HTTPS и редиректы на публикации того же источника; защита сайтов не обходится.

Для синхронных `/parse` и `/collect` запускайте один API worker. Их локальный
rate limit не объединён с очередью; при регулярном сборе используйте `/queue`
и отдельный воркер вместо параллельного запуска синхронного CLI/API-сбора.
Очередь и автоматические повторы описаны ниже. Обход списков и RSS пока не реализован. API предназначен для локального запуска.

## Очередь обработки

Очередь хранится в `news_raw` той же БД `PARSER_DATABASE_URL`, что использует API.
Задачи сохраняются после перезапуска. Добавлена таблица `queue_source_state`
для общего ограничения частоты воркеров; она создаётся при запуске без изменения
существующих колонок и данных.

### Поставить URL

`POST /queue` возвращает HTTP 202 и текущие задачи; сам запрос ничего не загружает.
До 100 URL за запрос, весь пакет валидируется и сохраняется одной транзакцией.
Повторная постановка того же нормализованного URL возвращает прежнюю задачу,
сохраняет её статус и не обнуляет попытки (включая `failed`).

```json
{"urls":["https://www.interfax.ru/business/1124538"]}
```

`GET /queue` — список (параметры `status`, `limit`, `offset`).
`GET /queue/{id}` — статус, число попыток, ошибка, время повтора и готовый текст.

### Запустить воркер

Во втором терминале из `services/parser`, с той же настройкой БД, что у API:

```powershell
.venv/Scripts/python scripts/run_worker.py
```

Воркер опрашивает БД раз в 2 секунды. Для одного прохода по доступным задачам:

```powershell
.venv/Scripts/python scripts/run_worker.py --once --limit 20
```

`--once` не ждёт будущих повторов или освобождения лимита источника. Если задача
пока недоступна, она останется в БД для следующего запуска.

### Состояния и повторные попытки

- `pending` — ожидает обработки.
- `processing` — захвачена воркером, попытка началась.
- `ready` — HTML, текст и метаданные сохранены.
- `retry` — временная ошибка, ожидает следующей попытки.
- `failed` — постоянная ошибка или лимит попыток исчерпан.

Сетевые ошибки, 429 и 5xx: максимум 3 попытки, паузы 60 и 120 секунд;
`Retry-After` учитывается, если требует более долгого ожидания.
403, прочие постоянные HTTP-ошибки и ошибки извлечения автоматически не повторяются.
При 403/429 источник приостанавливается минимум на 15 минут; другие источники
продолжают обрабатываться. Ошибка сохраняется в `last_error` и видна в API.

Захват атомарный: одна задача не выдаётся одновременно двум воркерам. После
15 минут без завершения задача может быть захвачена снова; запоздалое завершение
старого воркера не перезаписывает новый результат. Если последняя попытка тоже
зависла, задача после истечения этого срока переводится в `failed`.
Между стартами задач одного источника — не менее 5 секунд, общее состояние в БД
для всех воркеров. Сетевой запрос выполняется вне транзакции захвата.

Параллельный захват проверен на файловой SQLite. При сбое между загрузкой и
сохранением повторный сетевой запрос возможен; новая строка публикации не создаётся.
Неожиданные внутренние ошибки пишутся в лог воркера, задача восстанавливается
после истечения срока захвата. Ручной перезапуск `failed` через API пока не добавлен.


## Celery + RabbitMQ

Режим выбирается переменной `PARSER_QUEUE_BACKEND`: `local` (по умолчанию) или `celery`.
`/parse` и `/collect` остаются синхронными. В режиме Celery `POST /queue` сначала
сохраняет задачи в БД, затем отправляет их ID в RabbitMQ. Текст и результат в брокер
не помещаются. Статусы читаются прежними `GET /queue` и `GET /queue/{id}`.
Отдельный Celery result backend не требуется. ML-сервис не меняется; общая БД —
следующий этап, текущий `PARSER_DATABASE_URL` должен совпадать у всех процессов парсера.

### Локальный запуск

Docker Desktop должен быть запущен в режиме Linux containers. Из `services/parser`:

```powershell
uv sync --locked
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# Если .env уже есть, внесите настройки из примера вручную.
docker compose -f compose.rabbitmq.yaml up -d --wait
uv run --env-file .env scripts/init_db.py
uv run --env-file .env scripts/run_api.py
```

В отдельных терминалах, из того же каталога:

```powershell
uv run --env-file .env scripts/run_celery.py worker
```

```powershell
uv run --env-file .env scripts/run_celery.py beat
```

Нужны **оба** процесса: worker обрабатывает публикации, Beat каждые 10 секунд
запускает восстановительную отправку ожидающих задач. Запускайте один Beat на БД.
Прежний `scripts/run_worker.py` используется только в режиме `local`.
Файл `.env` загружается аргументом `uv --env-file`, сам Python его не читает.
Настройка `PARSER_BROKER_URL` — AMQP URL; пример соответствует локальному Compose.
Management UI: http://127.0.0.1:15672 (`parser` / `parser_local`, только локальная разработка).
Данные RabbitMQ сохраняются в именованном Docker volume.

На Windows скрипт использует `--pool solo --concurrency 1`. Celery официально
не поддерживает Windows ([официальная FAQ](https://docs.celeryq.dev/en/stable/faq.html#does-celery-support-windows)); этот режим предназначен для локальной проверки.
Для рабочего окружения запускайте worker и Beat на Linux/WSL2, с доступом к одной БД.
Для Linux можно настроить `--pool prefork --concurrency 2`.

### Доставка, сбои и повторы

- Задачи и результаты хранятся в БД. Новая таблица `parser_broker_dispatch` создаётся
  `init_db.py`; существующие публикации не изменяются.
- В брокере — долговечные очереди `parser.publications` и `parser.dispatch`, JSON,
  persistent messages и publisher confirms; подтверждение обработки позднее (`acks_late`).
- Публикация и транзакция БД не атомарны. Резервирование отправки действует 60 секунд:
  если API упал до/после отправки, Beat повторно доставит ожидающую задачу после истечения резерва.
- При недоступном брокере API возвращает 202 с сохранёнными задачами и полем
  `dispatch: {sent: 0, deferred: N}`. После восстановления RabbitMQ и Beat они будут отправлены.
- Повторные сообщения допустимы. Захват в БД, лимиты источников и защита от запоздалого
  завершения остаются общими для всех воркеров. Гарантия — at least once, не exactly once.
- Повторы сетевых ошибок и 5xx остаются в БД (60/120 секунд, максимум три попытки).
  Beat отправляет задачи по наступлению срока; Celery не ведёт второй счётчик попыток.
- При неожиданном падении обработчика захват сохраняется на 15 минут, затем Beat
  возвращает задачу в работу. Повторный сетевой запрос при аварии возможен.
- Cooldown 403/429 и пауза 5 секунд на источник проверяются в БД; ожидающие задачи
  не занимают Celery worker на время паузы.

Проверки: `uv run python -m unittest discover -s tests -v`. Тесты используют временные
SQLite-базы и HTTP-заглушки; отдельный тест запускает реальный Celery consumer с
транспортом `memory://`. Это не заменяет smoke-тест с запущенным RabbitMQ.


Проверка с настоящим брокером 24.10.2026: RabbitMQ 4.4.0, Celery 5.6.3,
Windows solo worker. Сохранённая при выключенном брокере задача №5 доставлена Beat
после запуска RabbitMQ: HTTP 200 от ЦБ, `ready`, одна попытка, 502 символа текста.
Повторная постановка URL вернула ту же готовую запись без нового сообщения.
Временные служебные control/reply/event очереди настроены как exclusive,
чтобы RabbitMQ не отклонял их как transient non-exclusive queues.


## Общая PostgreSQL-база

Установлен драйвер Psycopg 3. Запись выполняется прямо в согласованные
`news_sources` / `news_raw` / `news_quotes`, без промежуточной SQLite-копии.
Служебные таблицы очереди расположены в той же БД и схеме. Контракт:
[docs/news-schema.md](../../docs/news-schema.md).

```dotenv
PARSER_DATABASE_URL=postgresql+psycopg://parser_user:password@127.0.0.1:5432/rec_news
PARSER_DATABASE_SCHEMA=public
PARSER_AUTO_CREATE_TABLES=false
```

Для Docker укажите хост сервиса PostgreSQL (`db`), а не `127.0.0.1`.
У API, worker и Beat обязательно одинаковые настройки подключения.
Приоритет URL: `PARSER_DATABASE_URL`, затем `DATABASE_URL`, затем
`REC_NEWS_DATABASE_URL`. Если URL не задан, сохраняется SQLite для локальной разработки.
Сокращённые `postgres://` / `postgresql://` автоматически используют драйвер Psycopg 3.

Пул на один процесс: `PARSER_DB_POOL_SIZE=5`, `PARSER_DB_MAX_OVERFLOW=10`,
`PARSER_DB_POOL_TIMEOUT=30` секунд; таймаут подключения `PARSER_DB_CONNECT_TIMEOUT=10`.
Подключения PostgreSQL используют UTC. Имя схемы задаётся отдельно и проверяется.

Инициализация один раз до запуска процессов:

```powershell
uv run --env-file .env scripts/init_db.py
uv run --env-file .env scripts/init_db.py --check
```

На PostgreSQL обычный запуск не создаёт и не меняет таблицы, если
`PARSER_AUTO_CREATE_TABLES` не включён явно. `init_db.py` создаёт таблицы и добавляет
nullable `published_date` в старую `news_raw`; другие колонки и данные не изменяет.
Существующие SQLite-публикации автоматически не переносятся.

Проверки с настоящим PostgreSQL используют отдельную случайную схему на каждый тест,
которая удаляется после теста; рабочие схемы не очищаются:

```powershell
$env:PARSER_TEST_DATABASE_URL='postgresql+psycopg://test_user:password@127.0.0.1:5432/test_db'
uv run python -m unittest discover -s tests -p test_postgres.py -v
```

Пользователь тестовой БД должен иметь право создавать и удалять тестовые схемы.
Проверяются чтение готовой публикации отдельным SQL-потребителем, дубликаты,
конкурентная постановка и захват, сетевые повторы и восстановление захвата.
### Передача в ML

На PostgreSQL передача включена по умолчанию (`PARSER_ML_EXPORT_ENABLED=true`).
`PARSER_ML_NEWS_SCHEMA=ml_news` задаёт схему входной таблицы `news`; при отсутствии
настройки используется `{REC_NEWS_DB_SCHEMA_PREFIX}news`, по умолчанию `ml_news`.
В SQLite передача выключена, отдельные SQLite-файлы ML не заполняются.

Сначала ML-сервис должен создать собственную входную таблицу в общей БД.
Парсер не создаёт её и не меняет ML-схему. Затем выполните `scripts/init_db.py` парсера.
При запуске проверяется наличие таблицы ML и обязательных колонок.

Успешные `/collect` и worker записывают `news_raw.ready` и `ml_news.news.new` одной
транзакцией; при сбое передачи `ready` не фиксируется. ID ML — стабильный
`parser:{source_code}:{SHA256(url)}`. Повторная передача не перезаписывает запись ML
и не сбрасывает её статус обработки. Метаданные происхождения — в `extra.parser`.
Текст, заголовок, URL и источник доступны ML напрямую; парсер не выполняет анализ.
Готовые URL при повторной постановке также передаются без повторного скачивания.

Для ранее готовых строк общей PostgreSQL-базы:

```powershell
uv run --env-file .env scripts/export_news.py --after-id 0 --limit 100
```

Команда обрабатывает до 100 записей, выводит `last_id`; следующую пачку можно
передать с этим `--after-id`. Повторный запуск безопасен. Она не переносит данные
из SQLite в PostgreSQL. После появления новых входных строк их обрабатывает
конвейер ML; отдельные ML-команды RabbitMQ парсер пока не отправляет.
