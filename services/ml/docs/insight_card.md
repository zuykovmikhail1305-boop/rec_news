# Карточка инсайта

Карточка объясняет руководителю, что новость значит для его компании. Её строят несколько агентов,
у каждого блока свой агент, затем карточку проверяют код и отдельный агент-проверщик. Ответ разбит на
блоки, бэкенд и фронтенд работают с каждым отдельно.

Код: `news_pipeline/insights/`. Параметры: `[insight_card]` в `config/ml.toml`. Каталог продуктов
банка: `config/references/bank_products.json`.

## Ручки

| Ручка | Что делает |
|---|---|
| `POST /users/{user_id}/news/{news_id}/insight` | построить карточку или вернуть готовую. Готовая отдаётся сразу, если входные данные не менялись (`fingerprint`). Новая строится за 30–80 с. `?refresh=true` строит заново |
| `GET /users/{user_id}/news/{news_id}/insight` | готовая карточка без построения; `404`, если её ещё нет |
| `GET /users/{user_id}/news` | у каждой новости поле `insight`: краткая карточка (заголовок и чипы) или `null` |
| `POST /pipeline/run` с `{"insights": true, "insights_top": 5}` | после рекомендаций строит карточки для первых N новостей каждого пользователя. Этап `insights`, счётчик `insights_built` |

Ошибки: `404` — нет профиля пользователя или новости среди обработанных (`unique.db`).

## Как строится

```
контекст: публикации N1… · аналитика A1 · данные компании F1… · профиль
   │
   ├─ этап 1 (параллельно): fact · bank_view · ai_conclusion
   ├─ этап 2 (параллельно): risks · hypothesis · actions          ← видят блоки этапа 1
   ├─ этап 3 (параллельно): header · headline · bank_offer        ← видят всё написанное
   │      после каждого блока — программная проверка; ошибка → агент переписывает блок (до 2 раз)
   │
   ├─ агент-проверщик: вердикт по каждому блоку против источников
   │      блоки с ошибкой переписываются по его замечанию → проверщик ещё раз (всего до 3 проверок)
   │
   └─ сборка: блоки → InsightCard; «На чём основан вывод» и «Как получен вывод» строит код
```

**Источники в контексте.**
- `N1` — новость (полный текст).
- `N2…` — дубли и пересказы того же события из других изданий, по одному на издание, по убыванию надёжности.
- `A1` — фрагмент аналитики, выбранный под пользователя в рекомендациях. Если рекомендаций ещё нет, фрагмент подбирается сейчас.
- `F1…` — данные о компании из анкеты и датасета:
  - отрасль, регион, выручка;
  - продукты в банке (например, «есть кредиты»);
  - ВЭД;
  - отрасли поставщиков и покупателей;
  - концентрация платежей («75% поступлений — от одного покупателя»). Эти доли посчитаны кодом по `payment.db`, агенты могут их приводить.

Каждый агент видит только нужные ему группы: факт — только публикации, позиция банка — только событие и аналитику.

**Модели** (`[llm_tasks]`, задачи `insight_<блок>`):

| Блок | Задача | Класс → модель |
|---|---|---|
| Факт | `insight_fact` | universal → Qwen3.6 35B |
| Позиция Альфа-Банка | `insight_bank_view` | text → Kimi-K2.6 |
| Вывод AI | `insight_ai_conclusion` | reasoning → GLM-5.3-Flash |
| Риски / Возможности | `insight_risks` | reasoning → GLM-5.3-Flash |
| Гипотеза | `insight_hypothesis` | reasoning → GLM-5.3-Flash |
| Что можно сделать | `insight_actions` | reasoning → GLM-5.3-Flash |
| Шапка (чипы) | `insight_header` | reasoning → GLM-5.3-Flash |
| Заголовок | `insight_headline` | text → Kimi-K2.6 |
| Предложение банка | `insight_bank_offer` | universal → Qwen3.6 35B |
| Проверщик | `insight_verifier` | relations → DeepSeek-V4.1-Flash, модель не совпадает с авторами блоков |

**Программная проверка** (`insights/checks.py`). Ошибка отправляет блок на переписывание:

| Что проверяется | Коды |
|---|---|
| Числа есть в источниках | `invented_number` |
| Ссылки только на существующие и доступные блоку источники | `bad_source`, `no_source` |
| Вывод AI указывает особенности компании | `no_feature` |
| Тон Альфа-Банка: без драматизации, категоричности, «мы считаем» от имени банка, эмодзи и восклицательных знаков | `tone_*`, `bank_voice` |
| Без советов купить или продать | `trade_advice`, `tone_forbidden` |
| Позиция банка начинается с «Аналитики Альфа-Банка» | `bank_not_named` |
| Расхождение аналитики с новостью названо | `contradiction_missed` |
| Заголовок не пересказывает новость и не даёт совет | `headline_is_title`, `headline_is_advice` |
| Заголовок опирается на новость, аналитику банка (если есть) и особенности компании | `no_source`, `analytics_ignored`, `no_feature`, `unknown_aspect` |
| Гипотеза без «точно», «обязательно» и без советов | `forecast_words`, `hypothesis_advice` |
| Количество пунктов и длина | `count`, `too_long` |
| Продукт банка связан с названным риском | `offer_off_topic` |

Если после всех попыток остались ошибки, которые вводят в заблуждение (выдуманное число, чужой
источник, совет купить или продать, «мы» от имени банка), блок не показывается (`null`). С остальными
ошибками блок остаётся со статусом `unverified`.

**Без LLM** карточка строится в упрощённом виде (`status = degraded`):
- шапка: надёжность по числу изданий, приоритет по важности события, влияние и горизонт — `unknown`;
- факт: первые предложения новости;
- позиция банка: связка «новость ↔ аналитика» из рекомендаций;
- источники.

### Поля и как их показывать

| Блок | Поле | Что значит |
|---|---|---|
| Шапка | `impact.value` | `risk`, `opportunity`, `neutral`; `unknown` — без LLM |
| | `priority.value` | `high`, `medium`, `low` |
| | `horizon.value` | `1-3m`, `3-6m`, `6-12m`; `unknown` — без LLM |
| | `reliability.value` | `confirmed` — событие есть в 2 и более изданиях; `single_source` — пока одно. Считается кодом, не LLM |
| | `label`, `reason` | готовая подпись чипа и обоснование (для подсказки) |
| Заголовок | `text` | главная фраза: что событие значит для компании читателя. Пишет LLM по новости N1, аналитике Альфа-Банка A1 и профилю (роль, интересы, данные компании) |
| | `aspect` | интерес из профиля, который задевает фраза; `null`, если модель назвала интерес не из профиля |
| | `company_features` | особенности компании, через которые событие её касается |
| | `based_on_analytics` | фраза учитывает оценку аналитиков банка (`false`, если аналитики по теме нет) |
| | `company`, `role`, `event_date` | подпись «для какой компании и роли подготовлено, дата события» |
| Факт | `decided` / `discussed` | что уже решено и что только обсуждается. `discussed` пустой — показывать не нужно |
| | `key_figures` | ключевые цифры для выделения; `source_ids` — где они встречаются |
| Позиция банка | `available` | `false` — аналитики по теме нет: вместо блока показывается `warning` |
| | `material_title`, `material_date`, `url` | материал Альфа Ресерч и его дата |
| | `contradicts` | аналитика расходится с новостью — стоит выделить |
| Вывод AI | `company_features` | особенности компании, на которые опирается вывод (чипы-теги) |
| | `channels` | через что событие затронет компанию |
| Риски | `risks`, `opportunities` | по 1–3 пункта; `feature_ids` и `source_ids` — на что опирается пункт |
| Гипотеза | `text`, `disclaimer` | сценарий «если…, то…» и обязательная пометка, что это не прогноз |
| Что сделать | `steps`, `question` | 2–4 шага под роль и вопрос для обсуждения внутри компании |
| Предложение банка | весь блок | `null` — продукт не к месту (это нормально). `risk_index` — номер риска в `risks.risks` (с 0), с которым помогает продукт; `cta` — кнопка |
| На чём основан | `sources` | публикации: издание, надёжность 1–5 (`config/references/sources.json`), дословная цитата |
| | `analytics_material` | материал Альфа Ресерч и цитата из него |
| | `company_data` | учтённые данные о компании |
| | `trace` | шаги для кнопки «Как получен вывод» |

**`status` карточки:**
- `ready` — все блоки построены и проверены;
- `partial` — часть блоков не прошла проверку или не построена: показывать можно, но у таких блоков стоит пометка;
- `degraded` — без LLM.

**`verification.verdict`:**
- `passed` — проверщик принял карточку с первого раза;
- `passed_with_fixes` — после исправлений;
- `partial` — остались блоки с замечаниями;
- `not_verified` — проверщик не отработал.

**`verification.blocks.<блок>.status`:**
- `ok` — блок построен и прошёл проверку;
- `fixed` — исправлен по замечанию проверщика;
- `unverified` — замечания остались, блок показан;
- `failed` — блок не показан;
- `skipped` — блок не нужен (нет аналитики, нет подходящего продукта);
- `fallback` — запасной вариант без агента.

У каждого блока есть `issues`: замечания кода (`by: code`) и проверщика (`by: verifier`).

## Хранение — `data/insight_cards.db`

Таблица `insight_cards`, по строке на пару (`user_id`, `news_id`).

| Столбец | Что хранится |
|---|---|
| `user_id`, `news_id` | ключ |
| `card_id` | ID карточки (`ic_…`), новый при каждом построении |
| `event_id` | событие новости |
| `status`, `verdict` | `status` карточки и `verification.verdict` |
| `headline`, `impact`, `priority`, `horizon`, `reliability` | заголовок и чипы для ленты, без разбора JSON |
| `fingerprint` | отпечаток входных данных: профиль, анкета, публикации, фрагмент аналитики, данные компании, версии промптов. Изменился — карточка строится заново |
| `card` | карточка целиком (JSON `InsightCard`) |
| `generated_at`, `pipeline_version` | когда и какой версией построена |

## Стоимость и время

На API хакатона карточка строится за 30–80 с: 9 вызовов агентов блоков и 1–3 вызова проверщика,
плюс переписывания. Больше всего стоят два блока на Kimi: позиция банка и заголовок. Поэтому они
получают заголовок и лид новости, а не полный текст. Повторный запрос готовой карточки бесплатный.
Повторное построение с теми же входами берёт ответы из кэша LLM.
