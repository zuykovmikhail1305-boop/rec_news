# Как устроена ML-часть

ML-сервис (`services/ml`) получает новости из базы, склеивает их в события, подбирает к ним аналитику
Альфа-Банка, строит каждому пользователю персональную ленту, объясняет новости карточками инсайтов и
отвечает на вопросы в чате. Ручки и контракты — `docs/api.md`.

## Общая схема

```
бэкенд ──HTTP──► API (news_pipeline/api.py) ──► MLService (service.py) ──► компоненты
                       │  ставит задачи                                     │
                       ▼                                                    ▼
                очередь задач (tasks/) ──► обработчики ──► SQLite (data/*.db) или PostgreSQL (схемы ml_*)
                       processing.run                       + Qdrant (векторы)
                       insights.generate                    LLM API хакатона (llm/client.py)
                       analytics.analyze ◄── NewsDiscovered / AnalyzeNews (RabbitMQ, другие сервисы)
                       feeds.refresh     ──► AnalysisCompleted / AnalysisFailed (exchange analytics.events)
```

- **API** только принимает запросы, ставит долгую работу в очередь и читает готовые результаты из базы.
- **`MLService`** — один объект на процесс: держит компоненты, хранилища и очередь.
- **Очередь задач** выполняет обработку новостей и построение карточек: потоки внутри процесса API
  (`REC_NEWS_QUEUE=local`) или воркеры Celery с брокером RabbitMQ (`REC_NEWS_QUEUE=celery`, `docs/broker.md`).
- **Состояние** — запуски, задания, ленты, карточки, диалоги — хранится в базе, а не в памяти процесса:
  SQLite-файлы или PostgreSQL (`REC_NEWS_DATABASE_URL`).

## 1. Обработка новостей

`POST /processing.enqueue` создаёт запуск в `recommendations.db` (атомарно и только если другой не стоит
в очереди и не идёт) и публикует задачу `processing.run`. Её обработчик (`MLService.handle_processing`)
выполняет четыре этапа:

1. **Подготовка** (`preprocessing/`, `enrichment/`; `news.db` → `new_summary.db`). Очистка текста, лид
   (заголовок и 2–3 предложения), сущности, темы, важность 1–5, тип события (LLM Gemma). Статус новости
   `new → processing → ready`; запись, зависшая в `processing` дольше 30 минут, возвращается в `new`.
2. **Дедупликация и события** (`dedup/`; → `unique.db` и Qdrant). От дешёвых проверок к дорогим: хеш
   текста → тот же URL → почти копия (MinHash) → пересказ (эмбеддинги, подтверждённые сущностями, числами
   и LLM). Пересказы одного события из разных изданий получают общий `event_id`, продолжения сюжета —
   ссылку на родительское событие. Все издания-источники сохраняются (`news_sources`).
3. **Подбор аналитики Альфа-Банка** (`analytics/`; → `analytics.db`). Кандидаты из фрагментов аналитики
   ищутся по смыслу и по словам (BM25) с бонусами за общие сущности и темы; LLM-судья (DeepSeek)
   оценивает фрагменты 0–3 и тип связи (причины, прогноз, исторический контекст, противоречит, общая
   тема). Прикрепляется до 3 фрагментов с оценкой не ниже 2.
4. **Ленты пользователей** (`ranking/`; → `user_news`). Для каждого пользователя:
   - кандидаты за 7 дней из Qdrant по аспектам интересов;
   - `retrieval = 0.35·близость + 0.25·сущности + 0.20·темы роли + 0.10·важность + 0.10·свежесть`;
   - LLM-реранк (Gemma): оценка 0–3 «насколько важно этому человеку» и обоснование;
   - итог `0.6·LLM + 0.4·retrieval`; разнообразие: одно событие — одна новость, MMR
     (`mmr_lambda = 0.85`), не больше 3 новостей одной темы в топ-10;
   - фрагмент аналитики под интересы пользователя и связка «что аналитика говорит в контексте новости»
     (Kimi).

   Около 30 с на пользователя.

`GET /processing.result` отвечает `true`, когда обработка завершена и есть готовые новости. Повторная
доставка задачи пропускается; запуск, который идёт дольше `run_timeout_hours` (3 ч), считается упавшим.

## 2. Профиль интересов

`profile/`, хранится в `profiles.db`. Строится по анкете и данным компании из датасета (`dataset/*.db`):
отрасль по ОКВЭД, выручка, продукты в банке, ВЭД, отрасли поставщиков и покупателей по платежам.
Каждая компания считается отдельно, группы компаний не объединяются.

- LLM (Qwen) пишет 8–15 аспектов интересов: «стоимость заёмного финансирования — компания работает на
  кредитах». У аспекта есть описание, примеры, ключевые слова и вектор.
- Веса сущностей: своя компания 1.0, конкуренты 0.7, контрагенты и страны ВЭД 0.6, сырьё 0.5, регионы 0.3.
- Веса тем — по роли пользователя (`config/references/role_topics.json`, 13 ролей).

Профиль пересчитывается, только если изменилась анкета. Через API профили сейчас не создаются — из кода
(`MLService.build_profile`) и скриптов; читать их можно ручками `GET /profiles` и `GET /profiles/{user_id}`.
Факты о компании (`F1…`) считаются по датасету один раз на анкету и кэшируются; при старте API датасет
загружается и факты всех профилей считаются заранее, в фоне.

## 3. Карточка инсайта

`insights/`, хранится в `insight_cards.db`. Отвечает на вопрос «что эта новость значит для вашей
компании», разбивая ответ на блоки. Подробно — `docs/insight_card.md`.

**Вход:** публикации о событии `N1…` (новость и пересказы с надёжностью изданий), фрагмент аналитики `A1`,
данные компании `F1…` («есть кредиты», «75% поступлений — от одного покупателя»), роль и интересы.

**Агенты блоков** — по агенту (вызову LLM) на блок, три этапа, внутри этапа параллельно:

| Этап | Блоки (модель) |
|---|---|
| 1 | Факт (Qwen), Позиция Альфа-Банка (Kimi), Вывод AI (GLM) |
| 2 | Риски / Возможности, Гипотеза «если…, то…», Что можно сделать (GLM) |
| 3 | Шапка — чипы (GLM), Главная фраза из новости, аналитики и профиля (Kimi), Предложение банка (Qwen) |

**Проверки:**
1. Программная — после каждого блока: числа есть в источниках, ссылки на настоящие источники, тон
   Альфа-Банка, нет советов купить или продать, позиция банка подписана, главная фраза не пересказывает
   новость. Блок с ошибкой переписывается (до 2 раз).
2. Агент-проверщик (DeepSeek — другая модель) сверяет каждый блок с источниками; отмеченные блоки
   переписываются, всего до 3 проверок.

**Сборка кодом:** чип надёжности (по числу изданий), источники с дословными цитатами, учтённые данные
компании, шаги «Как получен вывод», статусы проверки по блокам.

Карточка строится 30–80 с и около 1,5 единицы бюджета LLM; готовая отдаётся мгновенно и строится заново,
только если изменились входные данные (отпечаток `fingerprint`).

## 4. Задания на карточки

`tasks/insight_jobs.py`, состояние в `jobs.db`. `POST /users/{id}/insights/generate` создаёт задание со
строкой на каждую новость ленты и публикует по задаче `insights.generate` на новость. Обработчик строит
карточку и записывает результат. Одновременно строятся `REC_NEWS_INSIGHT_WORKERS` карточек (по умолчанию 2);
готовые сразу видны в ленте. Задание можно отменить. Повторная доставка задачи пропускается.

## 5. Чат-агент

`agent/`, диалоги в `chat.db`. У каждого пользователя один текущий диалог: `POST /chat/{user_id}`
продолжает его, ML-сервис сам ведёт `session_id`. Устройство — `docs/agent_tz.md`.

1. **Контекст** — лента пользователя (`user_news`), поиск по базе новостей, фрагменты аналитики, профиль.
   Источники нумеруются (`N1…`, `A1…`, `P`) и фиксируются на диалог, чтобы уточнения ссылались на те же.
2. **Планировщик** (GLM) выбирает схему ответа из 7 (дайджест, влияние события, риски, позиция банка,
   сравнение, что делать, уточнение) и раздаёт источники разделам.
3. **Писатели разделов** (Kimi) — параллельно, со ссылками на источники.
4. **Программная проверка** — числа, ссылки, позиция банка только по аналитике, тон.
5. **Оценщик** (DeepSeek) — 7 критериев; не принято — разделы переписываются или ответ перепланируется.

В ответе позиция банка (`origin = bank`) отделена от выводов ассистента (`origin = ai`). Сообщения одного
пользователя обрабатываются по очереди. Ответ — 30–90 с.

## 6. Очередь задач

`tasks/`. Код знает только интерфейс `TaskQueue` (`publish`, `subscribe`, `emit`, `close`, `in_process`):

| Очередь | Задача | Обработчик | Одновременно |
|---|---|---|---|
| `processing.run` | `ProcessingTask` | `MLService.handle_processing` | 1 (блокировка `pipeline`) |
| `insights.generate` | `InsightTask` | `InsightJobs.handle` | `REC_NEWS_INSIGHT_WORKERS` / `--concurrency` |
| `analytics.analyze` | `AnalyzeNewsTask` (`news_id`) | `NewsAnalysis.handle` | подготовка — параллельно, дедупликация — по одной |
| `feeds.refresh` | `FeedsRefreshTask` | `NewsAnalysis.handle_feeds` | 1 |

Сообщения — JSON с полем `version`; обработчики принимают тело сообщения и не зависят от процесса, в
котором запущены. Обработчик просит повтор исключением `RetryLater`; после всех повторов — `on_give_up`
(у брокера сообщение уходит в очередь отказов `<очередь>.dlq`). Реализации:
- `LocalQueue` (`REC_NEWS_QUEUE=local`, по умолчанию) — потоки в процессе API: после рестарта
  незавершённые запуски и карточки ставятся заново;
- `CeleryQueue` (`REC_NEWS_QUEUE=celery`) — Celery + RabbitMQ: отдельные воркеры, приём `NewsDiscovered` /
  `AnalyzeNews` от других сервисов и отправка `AnalysisCompleted`; нужен Qdrant-сервер
  (`REC_NEWS_QDRANT_URL`). Подробно — `docs/broker.md`.

## 7. Общая инфраструктура

- **LLM** (`llm/client.py`) — один клиент для всех задач: модель под задачу (`[llm_tasks]` в
  `config/ml.toml`), кэш ответов (`llm_cache.db`), журнал вызовов с токенами и ценой
  (`data/logs/llm_calls.jsonl`), повтор при невалидном JSON, запасной режим без LLM.

  | Класс | Модель | Задачи |
  |---|---|---|
  | light | Gemma 4 26B | темы, важность, «то же событие?», реранк ленты |
  | reasoning | GLM-5.3-Flash | выводы и риски карточки, шапка, планировщик чата, судья оценки |
  | universal | Qwen3.6 35B | аспекты профиля, факт, предложение банка, синтетика |
  | relations | DeepSeek-V4.1-Flash | судья аналитики, проверщик карточки, оценщик чата |
  | text | Kimi-K2.6 | связка с аналитикой, позиция банка, главная фраза, писатели чата |

- **Хранение** — SQLAlchemy Core (`storage/db.py`; таблицы описаны рядом с кодом, колонки —
  `docs/news_db.md`): файлы SQLite в `data/` или, если задан `REC_NEWS_DATABASE_URL`, PostgreSQL — каждая
  база становится схемой (`data/news.db` → `ml_news`), код и запросы те же. Перенос данных —
  `scripts/migrate_to_postgres.py`. Векторы — Qdrant (локальная база `data/qdrant` или сервер по
  `REC_NEWS_QDRANT_URL`).
- **Настройки** — веса, пороги, версии промптов: `config/ml.toml`; тексты промптов с пояснениями: `config/prompts.toml`
  (читает `news_pipeline/prompts.py`); справочники (темы, роли, сущности,
  надёжность источников, тон, продукты банка): `config/references/`; подключения: `.env`.
- **Без LLM** все компоненты работают в упрощённом режиме: лента без реранка, упрощённая карточка
  (`degraded`), ответ чата подборкой источников (`fallback`).

## 8. Оценка качества лент

Оценка идёт только по размеченному набору `fixtures/eval_set/` (`news.jsonl` — новости, `labels.json` —
оценка 0–3 для каждой пары «пользователь — новость»; создаётся `scripts_for_tests/make_eval_set*.py`):

1. `scripts_for_tests/prepare_eval_news.py` — загружает набор в `data_eval/` (лишние новости удаляет,
   недостающие профили копирует из `data/`) и обрабатывает его тем же кодом, что `POST /processing.enqueue`;
2. `scripts_for_tests/eval_feed.py` — строит ленты четырёх версий (близость → сигналы → LLM-реранк →
   разнообразие) и считает по эталону nDCG@10, Precision@10, MRR, а также разнообразие, персонализацию,
   покрытие; LLM-судья оценивает топ-20 и сверяется с эталоном. Отчёт — `docs_utils/feed_eval_gold.md`.

На эталоне из 351 новости nDCG@10 рабочей ленты (v4) — 0,47, Precision@10 — 41 %.
