# Базы новостей: что хранится в каждом столбце

Код: `news_pipeline/storage/news_db.py`. Все базы — файлы SQLite. Код работает с ними через SQLAlchemy
(Core): таблицы описаны объектами `Table` в модуле, который с ними работает, а подключение и общие
операции собраны в `news_pipeline/storage/db.py`. Общие операции — создание таблиц и недостающих
колонок, `ON CONFLICT`, подсчёт изменённых строк. Новость проходит три базы:

```
news.db ──подготовка──► new_summary.db ──дедупликация──► unique.db
(входящие)              (очищенные и обогащённые)         (уникальные + события + источники)
```

| База | Таблицы | Кто пишет | Что лежит |
|---|---|---|---|
| `data/news.db` | `news` | `insert_news` (сервис новостей бэкенда), загрузка синтетики | входящие новости как пришли (архив всех поступивших) |
| `data/new_summary.db` | `news_summary`, `news_sources` (пустая) | `NewsSummarizer` | очищенные новости с лидом и обогащением (все подготовленные, включая дубли) |
| `data/unique.db` | `news_summary`, `news_sources`, `news_fingerprint` | `NewsDeduplicator` | уникальные новости с событиями, источники дублей, отпечатки |

## Статус обработки

Новости из баз не удаляются: у `news` и `news_summary` есть статус обработки. С `REC_NEWS_DATABASE_URL` базы — схемы PostgreSQL (`news.db` → `ml_news`, docs/broker.md), таблицы и колонки те же.

| `status` | Что значит |
|---|---|
| `new` | ждёт обработки |
| `processing` | этап взял новость в работу |
| `ready` | этап обработал новость |
| `failed` | только `news`: задача `analytics.analyze` не обработала новость после всех повторов (docs/broker.md); снова в работу — новая команда `AnalyzeNews` или статус `new` |

```
news.db:         new ──подготовка берёт──► processing ──записана в new_summary.db──► ready
new_summary.db:  new ──дедупликация берёт──► processing ──записана в unique.db / признана дублем──► ready
unique.db:       всегда ready
```

- **Ошибка этапа.** Пачка возвращается в `new` и обрабатывается следующим проходом.
- **Падение процесса.** Запись, зависшая в `processing` дольше 30 минут, снова получает `new`.
- **Повторно присланная новость.** Новость с тем же `document_id` не перезаписывается и сохраняет свой статус.

Векторы новостей лежат не в SQLite, а в Qdrant (`data/qdrant/storage`, коллекция `news`).

**Как хранятся данные.** У каждого поля метаданных — своя колонка. Списки и словари (сущности, темы,
числа) записаны в колонку как JSON-текст: в SQLite нет типа «массив». Источники новости — отдельная
таблица `news_sources`, по строке на источник. Пустые значения — `NULL`.

**Как это видит код.** Код конвейера работает с тем же словарём `metadata`, что и раньше (`metadata["source"]`,
`metadata["enrichment"]["topics"]`, `metadata["sources"]`…). Слой хранения сам раскладывает его по колонкам
при записи и собирает при чтении.

**Старые базы.** Базы прежнего формата с одной JSON-колонкой `metadata` переводятся в новый формат
автоматически при первом открытии.

## 1. `news` — входящие новости (`news.db`)

| Столбец | Тип | Что хранится | Пример |
|---|---|---|---|
| `document_id` | TEXT, PK | ID новости у источника; ключ на всём пути до `unique.db` | `syn_monetary_policy_1` |
| `text` | TEXT | полный текст как пришёл, абзацы через пустую строку | `МОСКВА, 15 октября. Банк России…` |
| `title` | TEXT | заголовок | `ЦБ сохранил ставку 14%` |
| `url` | TEXT | ссылка на оригинал | `https://tass.example/news/…` |
| `source` | TEXT | издание (домен); по нему считается рейтинг источника | `tass.example` |
| `rubric` | TEXT | рубрика источника, если есть | `Экономика` |
| `publication_time` | TEXT | время публикации, ISO 8601 с часовым поясом | `2026-10-15T10:24:00+00:00` |
| `created_at` | TEXT | когда новость поступила в сервис, ISO 8601 UTC | `2026-10-23T14:28:11+00:00` |
| `test_relation` | TEXT | **только синтетика**: `original`, `near_duplicate` (перепечатка), `semantic_duplicate` (пересказ), `continuation` (развитие события) | `semantic_duplicate` |
| `test_related_to` | TEXT | **синтетика**: `document_id` исходной новости для копий и продолжений | `syn_monetary_policy_1` |
| `test_event_key` | TEXT | **синтетика**: эталонный ключ события; у оригинала и его дублей он одинаковый, у продолжения свой | `monetary_policy_1` |
| `test_topic` | TEXT | **синтетика**: тема сценария из таксономии; `noise` — новость без влияния на бизнес | `денежно-кредитная политика` |
| `test_importance` | INTEGER | **синтетика**: важность сценария 1–5 | `5` |
| `test_genre` | TEXT | **синтетика**: жанр — `flash` (молния), `news`, `review` (обзор), `analysis` | `news` |
| `test_event_type` | TEXT | **синтетика**: тип события из сценария | `решение регулятора или правительства` |
| `extra` | TEXT (JSON) | прочие поля источника, для которых нет колонки; `NULL`, если их нет | `{"author": "…"}` |
| `status` | TEXT, индекс | статус обработки: `new`, `processing`, `ready`, `failed` (см. «Статус обработки») | `ready` |
| `status_updated_at` | TEXT | когда статус менялся последний раз, ISO 8601 UTC | `2026-10-23T14:36:05+00:00` |

Столбцы `test_*` — эталонная разметка для проверки дедупликации, событий и ранжирования. У реальных новостей они `NULL`.

## 2. `news_summary` — подготовленные (`new_summary.db`) и уникальные (`unique.db`) новости

Таблица одна и та же в двух базах. Столбцы из раздела «Дедупликация» заполнены только в `unique.db`.

### Текст

| Столбец | Тип | Что хранится |
|---|---|---|
| `document_id` | TEXT, PK | тот же ID, что в `news.db` |
| `text` | TEXT | очищенный текст: без ссылок, эмодзи, лишних пробелов и служебных хвостов («Подписывайтесь…», «Читайте также…»); абзацы через пустую строку |
| `title` | TEXT | заголовок |
| `first_paragraph` | TEXT | первый абзац (до первой пустой строки) |
| `audience_text` | TEXT | шаблон аудитории старого рекомендателя (`NewsAnalyzer`); сейчас пустая строка |

### Поля источника (копируются из `news.db`)

`url`, `source`, `rubric`, `publication_time`, `created_at`, `test_*`, `extra`, `status`, `status_updated_at` — то же, что в разделе 1.
В `new_summary.db` статус показывает, прошла ли новость дедупликацию; в `unique.db` он всегда `ready`.
В `unique.db` у `publication_time` есть запасное значение: если источник время не прислал, туда пишется время дедупликации.

### Подготовка (`NewsSummarizer`)

| Столбец | Тип | Что хранится | Пример |
|---|---|---|---|
| `lead` | TEXT | заголовок и первые 2–3 предложения; по нему считаются эмбеддинги и ищутся похожие | `ЦБ сохранил ставку 14%\nБанк России 15 октября…` |
| `prepared_at` | TEXT | когда новость подготовлена, ISO 8601 UTC | `2026-10-23T14:33:02+00:00` |
| `entities` | TEXT (JSON-список) | сущности: канонические имена из словаря (`config/references/entities.json`), регионы, организации и персоны из NER | `["Банк России", "Москва", "ОФЗ"]` |
| `topics` | TEXT (JSON-объект) | темы таксономии (`taxonomy.json`) и их вероятности 0–1; в новости только темы с вероятностью ≥ 0.15 | `{"денежно-кредитная политика": 0.92, "облигации": 0.4}` |
| `importance` | INTEGER | важность для крупного бизнеса 1–5: 5 — решение ЦБ или правительства для всей экономики, 1 — локальная новость | `5` |
| `event_type` | TEXT | тип события: `отчётность`, `сделка`, `регуляторика`, `решение регулятора`, `рыночная динамика`, `авария или ЧС`, `прогноз`, `другое` | `решение регулятора` |
| `numbers` | TEXT (JSON-список) | числа из текста в едином виде (запятая → точка); по ним проверяются дубли и инсайты | `["14", "15", "2026"]` |
| `enrichment_source` | TEXT | кто считал темы, важность и тип события: `llm` (модель Gemma) или `rules` (эмбеддинги и правила, если LLM недоступна) | `llm` |

### Дедупликация (`NewsDeduplicator`, только `unique.db`)

| Столбец | Тип | Что хранится | Пример |
|---|---|---|---|
| `deduplicated_at` | TEXT | когда новость прошла дедупликацию, ISO 8601 UTC | `2026-10-23T14:38:40+00:00` |
| `event_id` | TEXT | ID события. Пересказы и перепечатки одного события в разных изданиях имеют общий `event_id`: косинус ≥ 0.82 в окне 48 ч с подтверждением по сущностям и числам. Лента показывает одну новость на событие, аналитика подбирается к событию | `e_syn_monetary_policy_1` |
| `parent_event_id` | TEXT | ID события, которое эта новость развивает: похоже (косинус ≥ 0.65), до 21 дня раньше, есть общая сущность; `NULL`, если это не продолжение | `e_syn_inflation_3` |

## 3. `news_sources` — источники уникальной новости (`unique.db`)

Уникальная новость сохраняется одна, но её публиковали несколько изданий. Здесь по строке на каждую
публикацию: сама новость (`method = original`) и все найденные дубли. Пользователю это показывается как
«Источники: …», а ещё здесь видно, на каком шаге дедупликации пойман дубль.

| Столбец | Тип | Что хранится | Пример |
|---|---|---|---|
| `document_id` | TEXT | ID уникальной новости в `news_summary` | `syn_monetary_policy_1` |
| `position` | INTEGER | порядковый номер источника у этой новости (0 — она сама) | `0` |
| `source_document_id` | TEXT | ID публикации-источника: сама новость или её дубль | `syn_monetary_policy_1_near` |
| `url` | TEXT | ссылка на публикацию | `https://rbc.example/news/…` |
| `source` | TEXT | издание | `rbc.example` |
| `publication_time` | TEXT | время публикации, ISO 8601 | `2026-10-15T13:10:00+00:00` |
| `method` | TEXT | как найден: `original` — сама новость; `id` — тот же ID; `url` — тот же URL с точностью до `www`, `utm_*`, якоря; `exact` — тот же текст после нормализации; `near` — почти копия (MinHash, Жаккард ≥ 0.75); `semantic` — пересказ того же события (эмбеддинги) | `near` |
| `score` | REAL | уверенность: 1.0 для `id`/`url`/`exact`, Жаккард для `near`, косинус для `semantic`; `NULL` у `original` | `0.91` |
| `via` | TEXT | если дубль совпал не с оригиналом, а с другим дублем из той же пачки, — ID этого дубля | `syn_monetary_policy_1_para` |

Первичный ключ — (`document_id`, `source_document_id`): повторная обработка пачки не создаёт дубли строк.

## 4. `news_fingerprint` — отпечатки уникальных новостей (`unique.db`)

Нужны, чтобы дешёвые шаги дедупликации не считали эмбеддинги.

| Столбец | Тип | Что хранится |
|---|---|---|
| `document_id` | TEXT, PK | ID уникальной новости |
| `text_hash` | TEXT, индекс | SHA-1 нормализованного текста (регистр, ё/е, пробелы, пунктуация не различаются) — шаг `exact` |
| `url_key` | TEXT, индекс | нормализованный URL — шаг `url` |
| `minhash` | BLOB | MinHash по шинглам из 4 слов: 128 чисел uint64 подряд — шаг `near` (LSH) |

## Примеры запросов

```sql
-- сколько новостей ждёт подготовки
SELECT status, COUNT(*) FROM news GROUP BY status;

-- уникальные новости за неделю по важности
SELECT title, source, publication_time, importance, event_type
FROM news_summary
WHERE publication_time >= '2026-10-14'
ORDER BY importance DESC, publication_time DESC;

-- все публикации одного события
SELECT s.document_id, s.source_document_id, s.source, s.method, s.score
FROM news_sources s JOIN news_summary n USING (document_id)
WHERE n.event_id = 'e_syn_monetary_policy_1';

-- новости с сущностью «Банк России» (JSON-список)
SELECT title FROM news_summary, json_each(news_summary.entities)
WHERE json_each.value = 'Банк России';

-- вероятность темы
SELECT title, json_extract(topics, '$."денежно-кредитная политика"') AS p
FROM news_summary WHERE p >= 0.5;
```

## 5. `recommendations.db` — готовые рекомендации пользователям

Заполняется обработкой (`POST /pipeline/run`), читается ручкой `GET /users/{user_id}/news`.
Код — `news_pipeline/ranking/user_news.py`.

### `user_news` — какие новости подходят пользователю

Строка на пару «пользователь — новость», ключ — (`user_id`, `news_id`). При каждом запуске обработки
рекомендации пользователя заменяются целиком. Текст новости здесь не дублируется: он берётся из
`unique.db` по `news_id`.

| Столбец | Тип | Что хранится |
|---|---|---|
| `user_id` | TEXT, PK | ID пользователя (профиль в `profiles.db`) |
| `news_id` | TEXT, PK | `document_id` новости в `unique.db` |
| `rank` | INTEGER | место в ленте пользователя, 1 — самое важное |
| `event_id` | TEXT | событие новости; у пользователя не больше одной новости на событие |
| `score` | REAL | итоговая оценка 0–1: `0.6 · llm/3 + 0.4 · retrieval` (без LLM — `retrieval`) |
| `retrieval` | REAL | оценка без LLM: `0.35·sem + 0.25·ent + 0.20·topic + 0.10·imp + 0.10·fresh` |
| `sem` | REAL | близость новости к аспектам интересов пользователя (косинус, растянутый в 0–1) |
| `ent` | REAL | совпадение сущностей новости с важными пользователю (компания, конкуренты, контрагенты, сырьё, регионы, страны ВЭД): `1 − ∏(1 − вес сущности)` по совпавшим |
| `topic` | REAL | вес тем новости для пользователя: среднее весов тем профиля, взвешенное вероятностями тем новости |
| `imp` | REAL | важность новости: `(importance − 1) / 4` |
| `fresh` | REAL | свежесть: `exp(−часы/24)` от «текущего момента» обработки |
| `llm` | INTEGER | оценка LLM 0–3: насколько новость важна этому пользователю; `NULL` — LLM не оценивала |
| `why_relevant` | TEXT | почему новость важна пользователю (одно-два предложения) |
| `analytics_id` | TEXT | материал аналитики, выбранный под пользователя (`analytics.db`); `NULL` — подходящей нет |
| `analytics_chunk_id` | TEXT | фрагмент материала (`analytics_chunks.chunk_id`) |
| `analytics_relation` | TEXT | связь с новостью: `причины`, `прогноз`, `исторический контекст`, `противоречит`, `общая тема` |
| `analytics_contradicts` | INTEGER | 1 — аналитика банка расходится с новостью |
| `analytics_summary` | TEXT | связка «что аналитика говорит в контексте этой новости» для пользователя |
| `run_id` | TEXT | запуск обработки, который посчитал строку |
| `computed_at` | TEXT | когда посчитано, ISO 8601 UTC |
| `pipeline_version` | TEXT | версия ML-конвейера (`config/ml.toml`) |

### `pipeline_runs` — запуски обработки

| Столбец | Тип | Что хранится |
|---|---|---|
| `run_id` | TEXT, PK | ID запуска (`run_<дата>_<время>_<хеш>`) |
| `status` | TEXT | `queued`, `running`, `done`, `failed` |
| `stage` | TEXT | текущий этап: `prepare`, `dedup`, `analytics`, `recommend`, `insights`; `NULL` после завершения |
| `requested_at`, `started_at`, `finished_at` | TEXT | время запроса, начала и конца, ISO 8601 UTC |
| `demo_now` | TEXT | «текущий момент», от которого считались окно и свежесть (`NULL` — реальное время) |
| `news_prepared` | INTEGER | новостей подготовлено (`news.db` → `new_summary.db`) |
| `news_deduplicated` | INTEGER | новостей прошло дедупликацию |
| `news_unique` | INTEGER | из них уникальных (остальные — дубли известных событий) |
| `events_matched` | INTEGER | событий, к которым подбиралась аналитика |
| `users_total`, `users_done`, `users_failed` | INTEGER | пользователей к пересчёту, готово, с ошибкой |
| `insights_built` | INTEGER | карточек инсайтов построено (только при `insights: true`) |
| `error` | TEXT | текст ошибки, если `status = failed` |
