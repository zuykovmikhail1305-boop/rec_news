# Схема хранения HTML-публикаций

Общий контракт исходных публикаций: `news_sources`, `news_raw`, `news_quotes`.
Актуальная реализация парсера — `services/parser/parser_app/models.py`.
Парсер записывает готовые материалы со статусом `ready`; это статус извлечения текста,
а не завершения ML-обработки. В PostgreSQL схема по умолчанию — `public`.
Пользователи, анкеты и результаты ML остаются в своих согласованных таблицах.

## Создание таблиц

Из `services/parser`:

```powershell
uv sync --locked
# Указать подключение в .env по примеру .env.example, затем:
uv run --env-file .env scripts/init_db.py
uv run --env-file .env scripts/init_db.py --check
uv run --env-file .env scripts/run_api.py
```

Пример env для общей базы PostgreSQL:

```dotenv
PARSER_DATABASE_URL=postgresql+psycopg://parser_user:password@127.0.0.1:5432/rec_news
PARSER_DATABASE_SCHEMA=public
PARSER_AUTO_CREATE_TABLES=false
```

У API, local/Celery worker и Beat должны совпадать URL и схема БД.
В контейнерах хостом URL служит имя сервиса PostgreSQL, например `db`.
Имя самой базы и пользователь создаются администратором заранее.
`PARSER_DATABASE_URL` имеет приоритет над общими `DATABASE_URL` и
`REC_NEWS_DATABASE_URL`; при отсутствии всех трёх используется локальная SQLite.
`.env` загружается явно аргументом `uv --env-file`, переменные процесса имеют приоритет.

`init_db.py` создаёт отсутствующие таблицы и добавляет nullable-колонку
`news_raw.published_date`, если общей схеме её ещё не хватает. Данные не удаляются,
прочие таблицы не изменяются. Это ограниченное совместимое обновление, не полная
система миграций. `--check` проверяет схему без её изменения.
На PostgreSQL обычные процессы по умолчанию проверяют таблицы без DDL;
инициализацию нужно выполнить заранее отдельной командой. Для SQLite
автоматическое создание таблиц по умолчанию сохранено.

## Таблицы

- `news_sources`: `id`, уникальный `code`, `name`, `base_url`, `listing_url`,
  `parser_key`, `enabled` (по умолчанию true), `last_success_at`.
- `news_raw`: `id`, `source_id`, `url`, `title`, `raw_html`, `text`,
  `published_at`, `published_date`, `discovered_at`, `fetched_at`, `content_hash`, `status`,
  `attempt_count`, `next_retry_at`, `processing_started_at`, `last_error`,
  `parser_version`.
- `news_quotes`: `id`, `raw_id`, `quote_text`, `start_char`, `end_char`,
  `text_hash`, `created_at`.

Связи: `news_sources.id → news_raw.source_id`, `news_raw.id → news_quotes.raw_id`.
Удаление источника с публикациями или публикации с цитатами не каскадируется:
внешние ключи защищают сохранённые доказательства. Источник можно отключить
через `enabled`.

Публикация уникальна по `(source_id, url)`. URL нормализует адаптер перед
сохранением. `content_hash` — SHA-256 точного `text`, закодированного в UTF-8;
индекс не уникален, чтобы сохранять одинаковые тексты разных публикаций.
Есть индекс `(status, next_retry_at)` для выбора очереди.

Ссылка создаётся со статусом `pending`, пустыми текстом/HTML и нулём попыток.
Допустимые состояния: `pending`, `processing`, `ready`, `retry`, `failed`.
Переходы, блокировка задач и повторные попытки реализованы воркером парсера.
`ready` означает готовый извлечённый материал, а не готовый инсайт.

Даты адаптер передаёт в UTC с часовым поясом. PostgreSQL хранит timezone-aware
даты; SQLite не сохраняет информацию о часовом поясе: прочитанные наивные
значения следует интерпретировать как UTC. Серверные даты SQLite создаются в UTC.

## Цитаты

Создавать через `create_quote` из `app/news_quotes.py`, затем добавлять результат
в текущую SQLAlchemy-сессию. Функция проверяет:

```python
raw.text[start_char:end_char] == quote_text
```

Позиции — индексы символов Python (Unicode code points), начало включительно,
конец исключительно; это не байты и не индексы UTF-16 JavaScript.
Хеш всего текста вычисляется функцией, а не берётся на доверии из `content_hash`.
Ограничения БД дополнительно проверяют диапазон и длину цитаты; соответствие
содержимому другой таблицы проверяется именно функцией, не SQL CHECK.

При отображении/использовании цитаты после изменения статьи вызывайте
`quote_matches_text(quote, raw.text)`: изменённый текст делает старую цитату
невалидной, даже если цитируемые слова ещё встречаются. После перепарсинга
цитаты необходимо извлечь и проверить повторно. История версий текста пока
не хранится. HTML-парсер сам не выбирает доказательства будущего AI-вывода.

## Проверка

Из корня, с установленным SQLAlchemy из зависимостей проекта:

```sh
python -m unittest discover -s tests -p 'test_news_schema.py' -v
```

Тесты работают в отдельной SQLite-базе в памяти. Проверяют сохранность
существующих пользователей, повторную инициализацию, уникальность URL,
неуникальность хеша, ограничения БД, цитаты и компиляцию DDL PostgreSQL.
Последняя проверка не заменяет интеграционный тест на сервере PostgreSQL.


## Контракт чтения готовой публикации

`news_raw` содержит исходные HTML и извлечённый текст. Потребитель получает готовые
строки через `status = 'ready'`, соединяя `news_sources` по `source_id` для названия
и кода источника. ID публикации — `news_raw.id`; URL и хеш сохраняют происхождение.
Повторный сбор того же `(source_id, url)` не создаёт новую строку.
Если известна только дата, она сохраняется в `published_date`, а `published_at`
остаётся NULL: парсер не выдумывает время. `last_success_at` источника обновляется
после успешного сохранения публикации.

Состояния очереди и `parser_broker_dispatch` — служебные таблицы парсера в той же
настроенной PostgreSQL-схеме. Результаты анализа не должны заменять статус `ready`
парсера: потребителю нужен собственный учёт обработанных `news_raw.id`.

## Передача во входную таблицу ML

Принят контракт: парсер сохраняет исходный материал в `public.news_raw` и в той же
транзакции вставляет входную новость в `ml_news.news` со статусом `new`.
Это две таблицы одной PostgreSQL-базы. Сбой вставки ML откатывает запись `ready`;
очередь сохраняет захват для последующего восстановления и повторной обработки.

Таблицу ML создаёт и мигрирует ML-сервис; парсер проверяет её наличие и нужные колонки,
но не создаёт частичную копию и не изменяет её схему. Сначала выполните инициализацию
ML на общей БД, затем `services/parser/scripts/init_db.py` на той же БД.

- `document_id` — числовой ID публикации (`news_raw.id`) строкой, например `1542`; повторная
  передача той же публикации даёт тот же ID.
- Передаются полный `text`, `title`, канонический `url`, домен `source`, точное
  `publication_time` при наличии времени, время поступления `created_at` и `status=new`.
- В JSON `extra.parser` сохраняются `raw_id`, код источника, хеш текста,
  версия парсера и дата публикации (в том числе когда точное время неизвестно).
- `INSERT ... ON CONFLICT DO NOTHING` не сбрасывает начатую/готовую ML-обработку.
- Поддержаны `/collect`, worker очереди и повторная постановка готового URL.
  Для ранее собранных ready-строк есть `scripts/export_news.py --after-id 0 --limit 100`.

Настройки env: `PARSER_ML_EXPORT_ENABLED` (по умолчанию true для PostgreSQL,
false для SQLite), `PARSER_ML_NEWS_SCHEMA=ml_news`. Если задан общий
`REC_NEWS_DB_SCHEMA_PREFIX`, схема ML по умолчанию — `{prefix}news`.
Смена схем не переносит существующие данные автоматически.
Парсер не запускает классификацию и не меняет алгоритмы ML; ML забирает входные
строки своим конвейером. События/команды запуска анализа RabbitMQ ML этим изменением
не публикуются: реализована передача данных через общую БД.
