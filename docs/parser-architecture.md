# Архитектура парсера новостей (news-parser worker)

> Статус: проект на обсуждение · 2026-10-22 · кейс №1 «Новостная аналитика для принятия бизнес-решений»

## 1. Общая схема

Парсер — **отдельный воркер** (не часть FastAPI-приложения): собственный процесс,
собственный планировщик, общается с БД напрямую. API читает те же таблицы.

```
┌─────────────────────────────────────────────────────────────────┐
│                        WORKER (отдельный процесс)                │
│                                                                  │
│  ┌──────────────┐    ┌───────────────┐    ┌──────────────────┐  │
│  │ Планировщик  │───▶│  Этап 1: СБОР │───▶│ Этап 2: ОБогащение│  │
│  │ APScheduler  │    │  (без LLM)    │    │ (LLM, с бюджетом) │  │
│  └──────────────┘    └───────┬───────┘    └────────┬─────────┘  │
│                              ▼                     ▼            │
│                        news_raw               news_enriched      │
│                              │                     │            │
│                     news_source_rel ◀── трассировка ┘           │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    PostgreSQL / SQLite (alfa.db на MVP)
```

## 2. Этап 1 — Сбор (без LLM, ноль затрат)

**Расписание:**
| Источники | Тип | Интервал |
|---|---|---|
| Ведомости RSS, Коммерсантъ RSS, Интерфакс rss.asp, РИА RSS | RSS | каждые 15–30 мин |
| e-disclosure.ru, ЦБ РФ пресс-релизы | HTML | раз в час |

**Пайплайн этапа 1:**
1. Адаптер источника (по одному классу на RSS и HTML; источник = конфиг в YAML/таблице)
2. Нормализация: `title, text, published_at, url, source_id`
3. Дедупликация: SHA-256 заголовка + fuzzy (rapidfuzz ≥ 90) против последних N записей
4. Rate-limit: ≤ 1 запрос / 5–10 сек на источник, свой User-Agent, ретраи 3× с backoff
5. Запись в `news_raw` (всё подряд, без фильтрации)

**Эвристический префильтр (без LLM):** словарь ключевых слов, собранный из
ОКВЭД-кодов и категорий бизнеса профилей клиентов → помечает кандидатов
для этапа 2 (`relevance_hint`). Не отсеивает, только приоритизирует.

## 3. Этап 2 — Обогащение (LLM, бюджетный клапан)

**Модели (Приложение 3 кейса):**

| Роль | Модель | Задачи |
|---|---|---|
| Фильтр + теги | **Gemma 4 26B A4B** | классификация, извлечение — самая дешёвая |
| Сущности + summary | **Qwen3.6 35B A3B** | универсальная, извлечение/генерация |
| Интерпретация под клиента | **GLM-5.3-Flash** | рассуждения повышенной сложности |
| Ретро-анализ, большие объёмы | **DeepSeek-V4.1-Flash** | поиск взаимосвязей |
| Резерв | Qwen3-VL-30B, Kimi-K2.6 | мультимодал / запасной текстовый |

**Каскад (воронка экономии бюджета):**
```
news_raw (100%) ──эвристика──▶ кандидаты (~15–30%)
   ──Gemma: релевантность бизнесу──▶ прошедшие фильтр (~5–15%)
   ──Qwen3.6: сущности, теги, summary──▶ enriched
   ──(только для ленты клиента)──▶ GLM-5.3-Flash: интерпретация
```

**Бюджетный клапан:**
- Дневной счётчик токенов по каждой модели в БД (таблица `llm_usage`)
- Лимит кейса: 500 ₽/день на общий ключ
- Фактические цены неизвестны до первого дня → **день 1 — калибровка**:
  логируем токены/запрос, после замера выставляем лимиты и алерты
- При превышении: обработка откладывается до следующего дня, сбор продолжает работать

## 4. Схема данных

```sql
news_raw (
  id PK, source_id FK, url, title, text, published_at,
  content_hash UNIQUE, fetched_at, relevance_hint
)

news_enriched (
  id PK, raw_id FK→news_raw,
  relevance_score float, is_relevant bool,
  companies json, regions json, industries json,
  money_amounts json, tags json,
  summary text, trace_id
)

news_source_rel (        -- трассировка «источник → вывод»
  enriched_id FK, source_id FK, evidence_snippet, ground_type
)

llm_usage (
  id PK, model, prompt_tokens, completion_tokens,
  cost_rub, created_at, run_id
)
```

Формат обмена между этапами — JSON по фиксированной схеме
(`id, source, url, title, text, published_at, relevance_score, entities_json, tags, trace_id`).

## 5. Тесты

- Фейковая RSS-лента (генератор синтетических новостей по шаблонам)
- Проверка дедупликации: дубликаты заголовков, переформулировки
- Проверка каскада: что фильтр Gemma не теряет релевантное
- Синтетические данные — обязательное требование сдачи кейса
