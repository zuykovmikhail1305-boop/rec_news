# Единая БД для всех сервисов

## Принятое требование

По договорённости от 24.10.2026 вся информация приложения должна храниться в одной
общей БД. Разделение backend, parser и ML на независимые сервисы сохраняется.
Новые изменения хранения нужно проектировать с учётом этого требования.

## Текущее состояние

- Парсер хранит публикации, исходный HTML, источники и очередь в собственной SQLite-БД.
- ML использует отдельные SQLite-файлы для новостей, профилей, рекомендаций,
  аналитики, карточек, заданий и истории чата, а также отдельный индекс Qdrant.
- Backend получает профили и инсайты через ML API. Авторизация и cookie-сессии удалены.
- Данные, собранные парсером, пока автоматически не становятся входом ML:
  сервисы читают собственные данные. Общая БД ещё не реализована.

## Что учесть при объединении

1. Согласовать общую схему, идентификаторы публикаций, источников, компаний и профилей.
   Парсер сохраняет исходную публикацию, ML связывает результаты обработки с её ID.
2. В общей БД хранить исходные данные и результаты: HTML, текст, метаданные,
   очередь, статусы обработки, профили, аналитику, рекомендации, карточки и историю.
3. Назначить владельцев записи таблиц и единый порядок миграций схемы.
   Повторная доставка задачи не должна создавать дубликаты публикаций и результатов.
4. Отдельно согласовать перенос векторов из Qdrant в общую БД:
   сохранение отдельного хранилища векторов требует явного пересмотра требования.
5. Подготовить миграцию существующих данных с резервными копиями и проверкой связей,
   затем проверить путь «URL → сбор → обработка ML → инсайт в интерфейсе» на общих данных.

Конкретная СУБД и механизм миграций пока не выбраны. Подмена путей разных сервисов
одним SQLite-файлом сама по себе не объединяет их разные схемы и контракты.
Текущий коммит фиксирует требование, а не выполняет миграцию БД.
